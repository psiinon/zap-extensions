AI Assisted Authentication

This add-on adds a new authentication method which uses an LLM to drive a browser and login to the target website.

Unlike Browser Based Authentication, which relies on heuristics to find the username and password fields, this method sends the LLM a description of the current page (URL, title, visible text and form elements) at each step, along with the actions performed so far, and asks it to decide what to click, type or select next, repeating until it detects that login has succeeded or failed (or a maximum number of turns is reached).

The LLM Support add-on must be installed and configured with a working provider, since it is used to drive the login flow.

Hints

Some login flows have non-obvious steps that an LLM cannot infer just by looking at the page, for example choosing a specific option from a dropdown, or dismissing a cookie banner in a particular way. A free-text "Hints" field can be supplied (in the method's options or in the Authentication Tester dialog) to give the LLM this kind of guidance, for example: 
      Set the domain dropdown to Project1 before clicking Next.

TOTP Second Factor

Login flows that ask for a one-time code from an authenticator app (TOTP) are supported. The TOTP data is defined under the user's credentials, in the same way as for Browser Based Authentication: in the desktop the user dialog has a "TOTP" tab, in the Authentication Tester the "TOTP" fields are shown when this method is selected, and in the Automation Framework and the API the usual totp parameters are used (see below).

The user can supply either:

  • the shared secret, in which case a fresh code is generated whenever one is needed, or
  • a fixed code (for example 1234, as accepted by some test and demo applications), by setting the code as the secret and the algorithm to FIXED.

The LLM is told that a TOTP code is available (and how many digits it has) but never the code itself: like the username and password it only ever sees placeholders which ZAP replaces when performing the actions. The code can be entered either in a single field or in pages that use one input box per digit - in the latter case the LLM fills each box in turn.

If a second factor is requested but the user has no TOTP data the LLM reports MFA_REQUIRED and the authentication stops. Other kinds of second factors (push notifications, SMS or email codes, security keys) are not supported.

Converting to Client Script Authentication

Running the LLM to drive a browser on every authentication attempt would be slow and unreliable (since it depends on a third-party service). Instead, this method is only intended to be used once to work out how to login to a given page: while it drives the browser it records every successful action (discarding those recorded before the flow went back to an earlier page, for example when a one-time code was rejected), and on success it automatically builds a Zest script from those actions and switches the context to use Client Script Authentication with that script - which is then used for all subsequent (much faster and deterministic) authentication attempts.

If a script with the same name already exists (for example because AI Assisted Authentication was run before against the same login page) it is replaced.

When a TOTP code was entered the generated script references the {{TOTP}} variable (or {{TOTP_1}}, {{TOTP_2}}, ... for one input per digit), which is resolved from the user's credentials each time the script is run to authenticate, so the code is always current even when re-authentication happens much later. The variables are also parameters of the script, so it can be run manually ("Run with Params") by providing the current code.

Automation Framework

AI Assisted Authentication can be configured in the environment section of an Automation Framework plan using: 
      authentication:
        method: "ai"
        parameters:
          loginPageUrl:                 # String, the URL of the login page, mandatory
          browserId:                    # String, Browser Id to use, default: firefox-headless
          loginPageWait:                # Int, the time in seconds to wait after the login page has loaded, default: 5
          hint:                         # String, the free-text hint described above

As with Browser Based Authentication, credentials are supplied under the user in the usual way: 

      credentials:
        username: …
        password: …
        totp:                     # Optional, only needed if the login flow asks for a TOTP code
          secret:                 # String, the secret, or the code itself for the FIXED algorithm.
          period:                 # Int, the period. Default: 30
          digits:                 # Int, the number of digits. Default: 6
          algorithm:              # String, the algorithm, one of SHA1, SHA256, SHA512, FIXED. Default: SHA1

Once AI Assisted Authentication succeeds it automatically switches the context to Client Script Authentication, as described above. If you re-run the plan then the context will use the generated script rather than the LLM from that point onwards, unless the context's authentication method is explicitly reset back to "ai".

API

AI Assisted Authentication can also be configured via the ZAP API using the aiAssistedAuthentication action of the authentication API, which takes the following parameters:
NameMandatoryDescription
loginPageUrlYesThe URL of the login page.
browserIdNoThe browser to use, default: firefox-headless.
loginPageWaitNoThe time in seconds to wait after the login page has loaded, default: 5.
hintNoThe free-text hint described above.

The TOTP data of a user is set with the totpSecret, totpPeriod, totpDigits and totpAlgorithm parameters of the setAuthenticationCredentials action of the users API.
